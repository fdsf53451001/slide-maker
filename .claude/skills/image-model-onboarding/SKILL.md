# 接上一個新的生圖模型

**接一個新模型的預設動作是實測，不是「能跑就收工」。** 沒有量過的模型只是「有回東西」，不知道它回的是不是這條通道拿得到的最好結果——而預設值一旦訂下來，之後每一次生成都用它。

## 先讀這三處

1. `packages/core/src/image-options.ts` — 可調項介面本身（`ImageModelOptionSet`／`ImageOptionField`），以及「為什麼是宣告式的」那段
2. `packages/provider-openai/src/image-options.ts` — 已註冊的三組（Gemini 系／Grok Imagine／gpt-image），照它的形狀寫
3. AGENTS.md 裡影像相關的幾條 — 尤其 `imageSize:"2K"` 的實測依據、以及「影像的量測一律要用有內容的 fixture」

## 這份流程要防的四件事

- **沒量就訂預設值**。「看起來還行」不是依據。同一個模型換一個檔位可能讓銳利度差四倍（見下面 2026-07-31 那組數字），而那個差別在縮圖上看不出來。
- **只留一個「最優」值**。最優是對「這個專案的預設畫布與常見用途」而言；使用者可能要更快、更省、或更大。最優當預設，其餘實測可用的照樣列出來讓人選。
- **憑空列出沒驗證過的選項**。選項不是選好玩的：列一個端點不吃的值，使用者選了拿到的是 gateway 的不透明 400，比不給選項更糟。
- **在 transport 裡用模型名判斷**。猜不中就靜默少送欄位，而那與「沒寫過這段」長得一模一樣，沒有任何一步會失敗。模型名只准出現在 option set 的比對裡，因為那裡猜錯的後果是「UI 少一組選項」，看得見也改得掉。

## 步驟

### 1. 先跑通，並記下基線

在模型庫加一個 entry（連線、model id、影像 API），用預設生一頁。沒有 option set 的模型**一個尺寸欄位都不送**，所以這一次拿到的就是「這個端點自己的預設」——那是後面所有比較的對照組，要記下來，不是跑過就算。

**記這幾項**：回傳影像的原始像素尺寸與長寬比、銳利度（Laplacian 變異數）、0.87–1.0 頻段的高頻能量、端到端耗時、token 用量。

跑不起來的話先排查通道（下一節），排掉之後回到這裡把基線補齊。

### 2. 跑不起來時的分流

| 症狀                   | 可能原因                             | 先試什麼                                                             |
| ---------------------- | ------------------------------------ | -------------------------------------------------------------------- |
| gateway 400 / 端點拒絕 | 送了它不吃的欄位，或缺了它必要的欄位 | 換一條 `imageApi`（`chat`／`openrouter-image` 都不送尺寸）看是否就過 |
| 回了文字沒有影像       | 這個模型不支援影像輸出               | 換模型；不要試圖用 prompt 逼它                                       |
| 影像格式解不開         | 回了 transport 不認得的 mime         | 看 `image-util.ts` 支援的 raster 清單，缺的才是要補的                |

換通道能跑就繼續往下走——**能跑不等於跑得好**，基線還是要量。

### 3. 探出候選參數，逐一實測

先弄清楚這個端點在尺寸／解析度上吃哪些欄位與值（官方文件、gateway 的 translator 原始碼、或直接送一個明顯不合法的值看它的錯誤訊息會不會列出合法值）。把候選列出來，逐一跑。

**開跑前先跟使用者報成本**：幾個候選 × 幾次取樣 × 每次大約多少 token 與時間。這是花他的錢，但這一步不是可選的——沒跑就沒有預設值可訂。

量測規則，每一條都有實測教訓：

- **一定要用有內容的 fixture**（真實投影片，含文字、圖表、細線），**不可用純色或漸層測試圖**。2026-07-31 的實測裡，同一組改動拿純色圖估出來是「34.8 → 66.9、成本 +60%／+36%」，真實 fixture 是「99.3 → 430.1、成本 +17%／+16%」——收益低估五倍、成本高估三倍，兩邊都會導向錯的決定。
- **每個候選值至少取樣 3 次**。影像模型有隨機性，單次結果不足以排序。
- **量與基線同一組指標**，否則沒得比。
- **解析度與比例分開判斷**。兩者無關：非 16:9 時仍然要送解析度。反過來，送一個與畫布不符的比例會讓模型照錯的比例構圖，正規化再 cover 裁切一次就吃掉版面邊緣——那種情況寧可不指定比例。

**排序的判準是「正規化是放大還是下採樣」**：回傳尺寸小於畫布（1920×1080）就要放大，放大必糊；大於畫布是下採樣，反而更銳利。所以最優通常是「略大於畫布的那一檔」，不是最大的那一檔——更大只是更慢更貴，`4K` 回 5504×3072／9 MB 對這個畫布純粹是浪費。

### 4. 註冊 option set

在對應的 `image-options.ts` 加一組，照既有三組的形狀：

- `fields` 列出**所有實測可用**的值——最優當預設不代表其他的要藏起來
- `resolve({})` 回最優那一組——**預設與使用者的選擇走同一條路**，兩者才不會分岔成兩套規則
- `unsetLabel` 寫「沒選時實際會送什麼」（例如 `2K（模型預設）`），不要只寫「預設」兩個字
- **每個選項的依據寫進註解**：實測日期、量到的數字、為什麼這個是預設。沒實測過的值要嘛不列，要嘛明白註記「尚未實測」——像 Grok Imagine 那組就只有 `2k` 有實機依據，註解裡寫清楚了
- 比對模型名時先剝掉 vendor 前綴：同一個模型在不同 gateway 上寫法不同（`grok-imagine-image-2.0` vs `x-ai/grok-imagine-image-quality`）
- transport 也要篩：某家的欄位只有特定通道的 translator 認得，列在別條通道上等於給一個送出去會被忽略的選項

### 5. 驗證

- `packages/provider-openai/test/openai.test.ts` 的 `every choice an option set advertises actually reaches the request body` 會逐一送出每個宣告的選項並檢查 body。**新增 set 之後要在那條測試的 `cases` 表補一筆**——那條測試會斷言 `IMAGE_OPTION_SETS` 與 `cases` 一一對應，漏掉會直接紅。
- 伺服器端的寫入驗證不需要改：它比對的就是同一份宣告。
- `pnpm check` 必須全綠。
- 把實測數字寫進 commit 訊息，下一個人才有辦法判斷要不要重測。

## 禁止事項

- 不要在 `image-api.ts`／`image-chat.ts`／`image-openrouter.ts`／`provider-gemini/src/image.ts` 裡加任何模型名判斷。那幾個檔案只該認得 `ResolvedImageProfile`。
- 不要為了「保險」在 transport 層送一個猜的值。2026-08-29 拔掉的那個 `size:"1536x1024"` 就是這種：它只是剛好 OpenAI 吃，對別家是一個不透明的 400。
- 不要把 prompt 截短來換取「這個模型吃得下」。prompt 尾端依序是簡報內容、`UNTRUSTED_PRESENTATION_JSON` 隔離標記與注入防線，從尾端砍等於先砍掉安全邊界。長度不夠就用 `promptMaxBytes` 讓它明確失敗。
- 不要把實測沒跑過的值寫進 `choices` 充數。
